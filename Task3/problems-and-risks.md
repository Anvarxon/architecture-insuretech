# Задание 3: проблемы и риски текущей архитектуры

## Проблемы текущего взаимодействия

1. `core-app` и `ins-comp-settlement` зависят от синхронного REST API сервиса `ins-product-aggregator`.
2. `ins-product-aggregator` в рамках одного запроса обращается ко всем страховым компаниям и ждёт ответы от каждой из них.
3. Задержка или ошибка любой страховой компании увеличивает время ответа всего пользовательского сценария.
4. Рост количества страховых компаний с 5 до 10 почти линейно увеличит время агрегации и вероятность частичных отказов.
5. Периодический опрос каждые 15 минут и раз в сутки создаёт пиковую нагрузку и не гарантирует актуальность данных между запусками.
6. Локальные реплики продуктов в `core-app` и `ins-comp-settlement` обновляются независимо, поэтому возможна рассинхронизация тарифов.
7. `ins-comp-settlement` раз в сутки получает оформленные страховки через REST из `core-app`, что плохо масштабируется при росте количества продаж.
8. Суточная выгрузка оформленных страховок создаёт большой пакетный запрос и повышает риск тайм-аута, повторной обработки и пропуска данных.
9. Нет явного механизма идемпотентности, повторного проигрывания событий и гарантированной доставки между сервисами.
10. Отсутствие журнала событий усложняет аудит, восстановление локальных реплик и разбор инцидентов.

## Риски при росте нагрузки

1. Деградация `ins-product-aggregator` начнёт влиять на `core-app` и пользовательские сценарии.
2. Один медленный внешний API страховой компании может вызвать каскадные тайм-ауты.
3. Увеличение количества партнёров повысит вероятность ограничения частоты запросов и ошибок 5xx на стороне страховых компаний.
4. Ночная пакетная выгрузка в `ins-comp-settlement` может перестать укладываться в технологическое окно.
5. При повторных REST-запросах без идемпотентности возможны дубли в расчётах агентских премий.
6. Ручное восстановление локальных копий данных будет занимать много времени, что повышает RTO.

## Предлагаемое решение

1. Ввести потоковую передачу событий на базе Kafka-совместимого брокера.
2. `ins-product-aggregator` асинхронно получает данные страховых компаний, нормализует каталог и публикует события обновления каталога, изменения тарифа и недоступности страховой компании.
3. `core-app` и `ins-comp-settlement` подписываются на события продуктов и обновляют свои локальные проекции чтения без периодического опроса.
4. `core-app` публикует события по оформленным страховкам: заявка создана, полис выпущен, полис отменён, платёж получен.
5. `ins-comp-settlement` строит свою расчётную витрину из событий, а не запрашивает суточную выгрузку через REST.
6. Для событий, связанных с изменением собственной БД сервиса, использовать паттерн транзакционного исходящего журнала. Это нужно минимум в `core-app`; для `ins-product-aggregator` также применимо, если он хранит нормализованный каталог перед публикацией.
7. Для внешних API страховых компаний применить тайм-ауты, повторные попытки с нарастающей задержкой, автоматическое размыкание цепи и топик недоставленных сообщений для неуспешных интеграций.
