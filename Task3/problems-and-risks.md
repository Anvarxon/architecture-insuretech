# Task3: проблемы и риски текущей архитектуры

## Проблемы текущего взаимодействия

1. `core-app` и `ins-comp-settlement` зависят от синхронного REST API `ins-product-aggregator`.
2. `ins-product-aggregator` в рамках одного запроса делает fan-out во все страховые компании и ждет ответы.
3. Задержка или ошибка любой страховой компании увеличивает latency всего пользовательского сценария.
4. Рост количества страховых компаний с 5 до 10 почти линейно увеличит время агрегации и вероятность частичных отказов.
5. Периодический polling каждые 15 минут и раз в сутки создает пиковую нагрузку и не гарантирует актуальность данных между запусками.
6. Локальные реплики продуктов в `core-app` и `ins-comp-settlement` обновляются независимо, поэтому возможна рассинхронизация тарифов.
7. `ins-comp-settlement` раз в сутки получает оформленные страховки через REST из `core-app`, что плохо масштабируется при росте количества продаж.
8. Суточная выгрузка оформленных страховок создает большой batch-запрос и повышает риск timeout, повторной обработки и пропуска данных.
9. Нет явного механизма идемпотентности, replay и гарантированной доставки между сервисами.
10. Отсутствие event log усложняет аудит, восстановление локальных реплик и разбор инцидентов.

## Риски при росте нагрузки

1. Деградация `ins-product-aggregator` начнет влиять на `core-app` и пользовательские сценарии.
2. Один медленный внешний API страховой компании может вызвать каскадные таймауты.
3. Увеличение количества партнеров повысит вероятность rate limiting и 5xx на стороне страховых компаний.
4. Ночная batch-выгрузка в `ins-comp-settlement` может перестать укладываться в технологическое окно.
5. При повторных REST-запросах без идемпотентности возможны дубли в расчетах агентских премий.
6. Ручное восстановление локальных копий данных будет занимать много времени, что повышает RTO.

## Предлагаемое решение

1. Ввести event streaming на базе Kafka-compatible брокера.
2. `ins-product-aggregator` асинхронно получает данные страховых компаний, нормализует каталог и публикует события `ProductCatalogUpdated`, `TariffChanged`, `InsurerUnavailable`.
3. `core-app` и `ins-comp-settlement` подписываются на события продуктов и обновляют свои локальные read model без polling.
4. `core-app` публикует события по оформленным страховкам: `PolicyApplicationCreated`, `PolicyIssued`, `PolicyCancelled`, `PaymentReceived`.
5. `ins-comp-settlement` строит свою расчетную витрину из событий, а не запрашивает суточную выгрузку через REST.
6. Для событий, связанных с изменением собственной БД сервиса, использовать Transactional Outbox. Это нужно минимум в `core-app`; для `ins-product-aggregator` также применимо, если он хранит нормализованный каталог перед публикацией.
7. Для внешних API страховых компаний применить timeout, retry с backoff, circuit breaker и dead-letter topic для неуспешных интеграций.
